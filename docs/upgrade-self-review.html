塔台升级计划：自我审查回路

对标 pstack（Lauren Tan）的自我审查机器 · 目标：写完 ≠ 完成，审查通过才算 · 2026-11-08
一句话结论：pstack 最厉害的不是某个 skill，而是它把「自我审查」做成了 对抗性、并行、只有证据才成立、连审查者也被审计的流水线。我们的塔台现在只有机械验收 （文件在、Checks 非空）——这次升级把「语义级自我审查」装进每一个任务的交付管道： 交付 → 自审 → 对抗审查 → 修复 → 复检 → 反审计 → 沉淀。

一、pstack 的自我审查机器，拆开看 WHAT WE LEARNED

读了 thermo-nuclear-review、thermos、interrogate、 deslop、no-comments、reflect、show-me-your-work 的完整 SKILL.md（pstack 原版 + michael-denyer 的 Claude 移植版），它强在五条铁律：

1

审查者不是作者

thermo/interrogate 都是独立子代理拿着 diff 冷读，作者不在场——避免"自己查自己永远过"。
2

发现必须"跑出来"

interrogate 的规则：没有运行证明的发现不成立。每条 finding 必须带命令+实际输出； 风格类直接不要；"没有发现"是合法结果。
3

多镜并行 + 聚合去重

thermos 并行两个镜（bug/安全 + 代码质量），重叠的发现权重更高；分歧用自己的判断裁决。
4

审查者也被审计

no-comments 会拒绝审查者的越界/误报，退回重跑一次并把失败原因点名——审查权要靠质量挣。
5

审查完还要清场 + 沉淀

deslop 清 AI 味（改完必须重跑全部检查，检查挂了就回退）；reflect 把会话教训 路由进 skill 文件——教训变成结构，不是口头话。
它的审查合同里最值得抄的三句话：
① 「发现只允许关于本次新增/修改的代码」—— scope 纪律，不翻旧账；
② 「绝不带着没查完的研究发报告」—— "如果后端处理了就行"这种话不允许；
③ 「绝不虚报优先级——虚报会让开发者不再听你的」—— 误报有代价，审查者才有信誉。

四、分期实施 PHASES

P0 自审闸门 约 0.5 天 · 改 dispatch.py / verify.py / principles.py

机制

报告里新增 ## Self-review 必填区块。bot 交报告前必须：换脑重读自己的 diff（只审新增/修改）、 跑一遍 pstack 自审清单（下表）、发现的问题就地修完再交。区块允许写「no findings」——但 verifier 会 抽查（diff 里明显的问题而 Self-review 说 no findings → 打回）。

自审清单（写进 scaffold + 审查合同）来源
只审本次新增/修改的代码，不翻旧账thermo scope 纪律
追踪改动对其它文件的副作用（谁 import 了它、谁调了它）breaking-functionality 指南
Checks 逐条重跑，引用真实输出（不许"应该会过"）prove-it-works
清 AI 味：多余注释、防御性 try/except、嵌套过深deslop
不留解释性注释，约束改成结构/命名/断言no-comments
改完必须重跑全部检查；有检查挂了就回退该编辑deslop guardrail

改动面

  • CONTRACT（dispatch.py）：报告合同加 ## Self-review 段说明 + 清单
  • verify.py：accept_requires 增加 self_review 项（缺区块 → FAIL）
  • config：self_review: true（默认开）；self_review_roles: [] 按角色豁免
  • scaffold（principles.py）：清单写进 Work discipline

验收

  • 无 Self-review 区块的报告 → verify FAIL（回归测试）
  • 写 "no findings" 但 diff 有明显未处理问题 → triage 打回（规则 + 测试）
  • sync 行为不变：self_review: false 时全绿
P1 对抗审查（thermos/interrogate 化） 约 1 天 · 改 worker/triage + auditor 合同

机制

自审通过的报告（state=ready）在 triage 之前自动触发一次对抗审查派单给 auditor（或 review_roles 配置的角色）， 使用专门的 ADVERSARIAL_CONTRACT：

Break this change. Prove each finding with a run against the real code —
a failing test, a repro script, or command output showing wrong behavior.
Report each finding: title / exact command / actual output / output the intent requires.
Leave out anything you did not run. Style, naming, structure: out of scope.
No findings is a valid result. Never misreport priority — false alarms
spend the trust this review runs on.

规则：

  • 异步并行：审查派单走 0.9.x 的 async 队列，不阻塞原任务；可配置双镜 （review_roles: [auditor, qa]）——重叠发现权重更高，聚合去重
  • 发现才有资格打回：带 repro 的 finding → 原任务 rework（附 repro）； 无 finding → 自动 accept；审查者自己跑不出证明的发现直接丢弃（triage 验证 repro 可执行）
  • 预算：审查占一轮（review_budget: 1），不无限循环；auditor 超时 = 视为 pass + 通知
  • events：adversarial_started / finding(proved|dropped) / adversarial_verdict

数据模型

task.json += { "review": {"verdict": "pass|rework", "findings": N, "proved": N,
                            "dropped": N, "reviewer": "auditor", "ts": …} }

验收

  • mock 场景：auditor 报 1 个带 repro 的 finding → 原任务 rework 且 brief 含 repro；auditor 报 0 → accept
  • auditor 的 finding 无 repro → 被 triage 丢弃并计数（dropped）
  • async：审查本身 <1s 入队；结算走 inbox
P2 反审计（审查者治理） 约 0.5 天 · 改 triage.py

机制

抄 no-comments 的治理：triage 处理 auditor 发现时执行审查者审计——

  • 越界（finding 指向非 diff 文件）→ 丢弃 + 计数
  • repro 重跑不成立 → 丢弃；同一审查者一轮内被拒 ≥2 次 → 该轮报告判废，退回重跑一次并点名失败原因；再犯 → 上报 open issue
  • 误报优先级（把 medium 报成 high）→ 降权并记录信誉分（.tower/reviews/.json 信誉分）
  • 信誉分进入派单决策：低信誉审查者的 finding 需要第二意见

验收

  • 构造越界 finding / 假 repro / 误报 high → 各自被治理（3 条测试）
  • 信誉分落盘且可查询（tower status 显示 auditor 信誉）
P3 学习沉淀（reflect 化） 约 0.5 天 · 改 skills.py + 新 reflect 流程

机制

任务 accepted 时自动做一次轻量 reflect：扫本次的 rework 原因 + Self-review 发现 + 对抗 findings，问一句「这条教训是一次性的还是结构性的？」——结构性的自动生成 skill 草稿（tower skill save --draft），lead 一键采纳。教训从此进结构： 下次同角色派单自动注入（现有技能索引机制）。

验收

  • rework ≥2 次的同因任务 → 自动产出 skill 草稿（测试）
  • 草稿采纳后，下次派单 prompt 出现该 skill 行（现有机制回归）
P4 决策轨迹 + 面板可见 约 0.5 天 · 面板/scene 小改
  • 长任务（>3 步或多轮）要求 <task>-decisions.tsv：ts/phase/decision/why/evidence/result（show-me-your-work 格式）
  • verifier 对长任务检查该文件存在且 evidence 列是路径/SHA（不是散文）
  • scene：自审中=放大镜气泡、被审中=盾牌气泡、审查通过=短暂绿闪
  • 面板 KPI 增加「审查通过率 / 平均 findings / dropped 误报率」

七、风险与回滚 RISKS

风险对策
审查派单消耗 token/时间翻倍review_budget=1；只对 diff 审；mock/小任务可 review_roles: [] 关闭
审查者误报洪水反审计（P2）+ 信誉分 + "必须跑出来"门槛从源头过滤
循环依赖（审查触发的 rework 再触发审查…）review 预算只算 1 轮；rework 由 triage 正常预算管
自审流于形式（全写 no findings）verifier 抽查 + 对抗审查兜底（两道闸，不是自觉）
回滚三项配置全部默认可关：self_review: false / review_roles: [] / decision_trail: off 即回到 0.9.2 行为

八、总验收清单 ACCEPTANCE

  • 每个任务的报告含 ## Self-review；缺失 → verify FAIL（有测试）
  • ready 任务自动触发一次对抗审查；带 repro 的 finding → rework；无 finding → accept（mock 端到端测试）
  • 无 repro 的 finding 被丢弃且计数；越界 finding 被治理；误报退回重跑并点名原因（3 条测试）
  • accepted 后同因 rework ≥2 → 自动 skill 草稿；采纳后下轮派单可见（回归）
  • 10 任务并发走完「交付→自审→审查→验收」全链无死锁（.lock 压测）
  • scene 与面板能看出"审查中 / 审查通过率"
  • 全部开关关闭 = 0.9.2 行为，回归全绿
设计哲学对齐：pstack 的自我审查之所以强，是因为它不信任任何"说完成了"的声音—— 包括它自己派出去的审查者。我们照搬的不是 skill 文件，是这个立场： 每一层都要拿出跑得出来的证据，每一层都 accept 下一层、audit 上一层。 塔台的台账、verifier、Attention、skill 沉淀正好是承载它的地基——这次是把回路接通。
